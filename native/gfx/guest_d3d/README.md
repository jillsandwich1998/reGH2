# native/gfx/guest_d3d - the game's D3D library, hooked (G.0, option A)

The game does not draw through the kernel: the XDK's Direct3D library is **compiled into the XEX** (block `0x823C0000-0x823E0000`, 429 functions,
no symbols) and writes PM4 packets into a command buffer itself. Option A hooks that library's functions instead of processing the packets. This
directory holds the hooks, the discovery tools that found what the functions are, and an observer that proves the hooks can identify, at the moment
a draw is bound, exactly which shader the game is using and map it to the validated SPIR-V (`native/gfx/shader_cache`).

Nothing here draws. The original functions always run; the hooks only report. The Vulkan renderer is not connected to the window.

```
include/gh2gfx/guest_d3d.h   the contract: guest function addresses, structure layouts, the Observer interface (hooks -> whoever listens)
d3d_hooks.cpp                the hand-written hooks (guest side: shim headers only, built into gh2rt_hooks): 2 shader creations + the draw-state commit
include/gh2gfx/d3d_probe.h   discovery probe (GH2_D3D_PROBE=<prefix>): records the arguments of every function of the block
d3d_probe.cpp                the recorder          d3d_probe.gen.cpp   generated by tools/gen_d3d_probes.py: one observing hook per function (429)
semantic_hooks.txt           functions with a hand-written hook (the generator skips them; two hooks cannot own one symbol)
observer.{h,cpp}             ShaderObserver: container hash at creation, microcode at bind, correlation with shaders.pak (plain C++, links shader_cache)
observer_install.cpp         GH2_D3D_OBSERVE=<dir of shaders.pak> [GH2_D3D_REPORT=<json>] registers it       observer_selftest.cpp   offline test (fake guest memory)
```
Tools: `native/tools/gen_d3d_probes.py` (regenerate the probe hooks), `native/tools/d3d_probe_report.py` (read a probe recording), and in `work/analysis`
`d3d_funcs.py` (the PowerPC listing that the generated code carries in its comments, one function at a time).

## What the library does (CONFIRMED against the running game unless marked)
| Guest function | Role | Evidence |
|---|---|---|
| `sub_823CBE80(container)` -> object | **create vertex shader** | probe: receives a `0x102A1101` container, returns the object; 1283 calls while loading |
| `sub_823CBD70(container)` -> object | **create pixel shader** | probe: `0x102A1100` container; 1284 calls |
| `sub_823D4CC8(device, dirty)` | **commit draw state**: patches the microcode to the vertex declaration, writes `IM_LOAD` packets, moves the command pointer | read from its code; the observer parsed 4.2 M `IM_LOAD` packets it wrote, 100% consistent |
| `sub_823C6FB8`, `sub_823C74D8`, `sub_823C7A08`, `sub_823C7DF0` | the four draw functions: each calls the commit and then writes `DRAW_INDX` (HYPOTHESIS: DrawVertices / DrawIndexed variants; primitive type is r4) | static call graph + probe arguments |
| `sub_823D22B8(device)` | reserves command-buffer space, returns the write pointer | read from its code |
| `sub_823DF1A8` -> `sub_823DF0C0(function, out)` | builds a **constant-table** object (D3DX `CTAB`) from a container or D3D9 bytecode. It is NOT the shader | read from its code (`CTAB` lookup, 32-byte object) |
| `sub_823C6B50` | the spin-wait step (already hooked in `rt/hooks`) | earlier phase |

Structure layouts (all big endian in guest memory; `gh2gfx/guest_d3d.h` has them as constants):
- `D3DDevice`: `+12556` bound pixel shader object, `+12560` bound vertex shader object, `+48` address of the **last written** command-buffer dword (pre-increment).
- Shader object: the creation functions copy the container's *virtual* part (header, constants) into the object (`+40` for pixel, `+872` for vertex: vertex
  objects carry 832 more bytes of per-declaration fetch state) and the *physical* part (the microcode) into a separate GPU-visible allocation whose
  address is stored at `+24` (pixel) / `+32` (vertex). Inside the copied header, the u32 at `+24` is the offset of the shader struct `{microcode offset, bytes}`.
- `IM_LOAD` (`0xC001 2700`): dword1 = physical address | shader type (0 vertex, 1 pixel); dword2 = `start << 16 | size in dwords`. The physical address
  is `(v & 0x1FFFFFFE) + (((v >> 20) + 0x200) & 0x1000)` of the object's microcode address (the library's own conversion).

## Measured (2026-10-24, this machine, shader cache = the 636 containers: 633 from the ARK + 3 embedded in the XEX)
| Scenario | draw-state commits | shaders bound that the hooks had seen created | ... found in the cache | distinct (VS, PS) pairs |
|---|---|---|---|---|
| logos + intro video (35 s) | 1 406 | 100% (VS and PS) | 100% | 3 |
| title screen (30 s) | 17 050 | 100% | 100% | 7 |
| Quick Play song (70 s) | 2 362 750 | 100% | 100% | 89 |
- Zero bound objects the creation hooks had not returned, zero malformed containers.
- **Pixel microcode at bind is bit-identical to the container's** (1 958 575 of 1 958 575 `IM_LOAD`s in the song).
- **Vertex microcode at bind is the container's with 1 to 18 words rewritten by the library** (2 245 046 of 2 245 046: 1-2 words 31 864, 3-6 613 146,
  7-18 1 600 036; never identical). The rewritten words are inside the 3-dword vertex-fetch instructions: dword 1 bits 16-21 and a flag, dword 2 low
  byte = a small integer 5-9, dword 2 next bits = a small offset (HYPOTHESIS: format / stride / offset of the vertex declaration; `GH2_D3D_DUMP_PATCHES=N`
  prints N examples). So the shader identity is the container; the vertex layout is data the renderer gets from the declaration or from those words.
- The 3 containers that were missing from the ARK-only cache live at guest `0x820B6F28` (vs, 240 B), `0x820B7018` and `0x820B71E0` (ps, 452 B each): static data
  of the XEX (the video player's shaders). `shader_pipeline.py --pe default.pe` finds them with the same header scan.
- Cost: 60.2-60.3 fps in a song with the hooks idle, with the observer on and with the probe on (frames over 20 ms: 16 / 13 / 13).

## Running it
- `GH2_D3D_OBSERVE=<dir with shaders.pak>` (+ `GH2_D3D_REPORT=<file.json>`, `GH2_SHADER_DUMP_UNKNOWN=1`, `GH2_D3D_DUMP_PATCHES=12`): one summary line to stderr every 10 s, JSON at the end.
- `GH2_D3D_PROBE=<prefix>`: records `<prefix>.events` / `.functions` (first 1500 calls of each function; 64-byte records), then
  `d3d_probe_report.py <prefix> summary | containers | follow ADDR | object VALUE | created ADDR ARG`.
- `gh2_d3d_observer_selftest <dir with shaders.pak>`: the observer against a fake guest memory.

## What was NOT known after G.0 (now answered by Phase 2.6, below)
The setters of the bound shaders (they write device `+12556/+12560`), the vertex declaration and stream-source functions, texture and sampler setters,
render-target / depth setters, resolve, the swap, constant uploads, and everything about MSAA. The probe recording of a title run already lists 174
called functions; each needs the same treatment (static reading + argument evidence) before it is hooked. Only scenes seen so far: intro, title, one
Quick Play song; career/venues/loading screens may bind other shaders (all of them were created through `sub_823CBE80/CBD70` in every run so far).

## Phase 2.6 - the rest of the state of a frame (2026-10-24)

The library is bigger than G.0 assumed: the device methods (SetStreamSource, SetIndices, SetTexture, the sampler states) sit **below** 0x823C0000, from about
0x823BB8C0; the probe now covers 0x823B0000-0x823E0000 (912 functions). Everything below was read from the recompiled code and then checked against the
running game (window recordings with `d3d_window_report.py`, and the observer's verify mode).

**Completeness of the draw hooks (static fact):** the only functions in the executable that build a DRAW_INDX packet header are `823C6FB8`, `823C74D8`, `823C7A08`, `823C7DF0`
(geometry) and, for RECTLIST draws, `823C0D60` (clears), `823C2770` (resolve), `823C9C40` and `823DCA20` (init paths); the last two never ran in the scenes below.
**Device layout** is in `include/gh2gfx/guest_d3d.h` (`layout::`). **Fetch constants:** the library keeps the GPU registers 0x4800.. as a shadow at device+1024 (32 slots x 6
dwords) and flushes the dirty ones verbatim into the command buffer.

**Facts that matter for the renderer**
- The shader containers translate to SPIR-V with **semantic** vertex inputs (XenosRecomp keys each vfetch by its address in the container's element table). The layout of a
  draw is therefore: container element table (usage) + the library-patched vfetch instructions (fetch constant -> stream, stride, offset, format) + the stream's fetch constant.
  `fetch_scan.cpp` extracts exactly those from the microcode in memory (same walk as XenosRecomp's recompiler).
- `SetTexture(sampler, NULL)` clears the pointer but **leaves the fetch constant the GPU reads untouched**: 5 882 draws of the song sample a sampler whose D3D pointer is NULL and
  whose GPU constant is still the previous texture. A renderer must key textures by the fetch constant (base address), not by the object pointer.
- Depth-only passes exist (723 650 draws of the song have no colour target, a depth surface is bound).
- Mip-level resolves: `Resolve` with level (r8) 1..3 writes inside the destination texture's chain (111 744 in the song).

"Resolved" = the pipeline is known, the declaration, every stream the patched vertex shader reads, the index buffer (indexed draws), every sampler a shader reads (or the stale GPU constant
found by base address) and a colour or depth surface are registered resources. Verify mode compares, per draw: the device fields with the tracked bindings, the fetch constants in the
shadow with the headers of the bound resources, the DRAW_INDX packet (primitive, count, source, DMA base/size) with the call, every fetch-constant register the draw wrote with the
shadow, and the resolve's RB_COPY_DEST_BASE with the texture. **The 175 song mismatches (0.00005%) are unexplained residue**: 5 draws whose command range holds no DRAW_INDX, 4 fetch
registers, 166 resolves with a null source rectangle whose destination is far from the tracked texture. Command-buffer chunk jumps (>32 KB between the pointer before and after a draw)
are skipped (5 923 of 3.9 M draws). Inline-vertex draws are not parsed at the packet level.
